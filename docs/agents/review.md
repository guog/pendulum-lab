# 审查与提交前检查

先固定基线提交及实际审查对象。审查已提交变更时使用固定提交 SHA；审查待提交变更时先暂存拟提交文件，用 `git write-tree` 固定索引树，再用 `git diff <base-sha> <tree-sha>` 审查。记录未暂存和未跟踪文件，确认它们不属于本次提交；不要自动暂存无关内容。提交前再次运行 `git write-tree`，确保树与审查对象完全相同；如有变化，重新审查变化。

对约束和状态转换，检查进入、保持和退出边界，包括边界前、边界上、边界后及双向变化。检查同时发生的输入、约束与终止事件的优先级，使用独立推导或数值反例核对结果，并确认失败、不可用及恢复路径；避免只验证顺利路径或重复实现公式。

规格来自 Issue 时，先运行 `node scripts/collect-spec.mjs <owner/repo> <编号> <输出.json>`，把收集到的子任务和父规格交给 Spec 审查代理。工具追踪原生父 Issue、`Part of #编号` 和 `## Parent` 中的同仓库 Issue 链接；依赖项不自动作为父规格。读取正文中承担约束的补充决策链接；收集失败时先修复访问问题，不能当作“无规格”。

Spec 审查逐项给出需求到实现/验收证据的对应，明确延期或不适用项及其依据，覆盖父规格的继承要求。已冻结的字段名、版本和标识用独立契约测试核验；跨文件语义等判断仍由审查负责，不把尚未冻结的机器 schema 推定为新增字段要求。维护工作无 Issue 时，以用户确认的任务说明为规格，并保留来源和验收范围。

工具入口、输入和限制见 [预检和浏览器测试](workflow-tools.md)。检查结果不能替代对实际差异和需求的审查。
